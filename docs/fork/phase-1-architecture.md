# Fork Phase 1: Durable History, UI, and Drift

Status: proposed

This fork adds durable operational history around Atlantis's existing command and project execution. It does not introduce a durable work queue, detached workers, or a second command interface.

## Execution shape

The accepted command path remains:

```text
VCS event or authenticated API request
  -> existing command workflow
  -> existing project execution
  -> Terraform or OpenTofu
```

Durable history observes that path:

```text
accepted operation -> RunStore (PostgreSQL)
project lifecycle  -> RunStore (PostgreSQL)
command output     -> chunked RunStore writes (PostgreSQL)
plan binary        -> existing PlanStore (S3-compatible storage)
runtime locks      -> existing BoltDB or Redis database
```

PostgreSQL is not a replacement for Atlantis's existing locking or pull-status database. The S3-compatible `PlanStore` remains authoritative for binary plan artifacts; PostgreSQL stores only artifact references and history.

## Module seams

`server/core/runs` owns storage-neutral Runs, Project Runs, Output Chunks, Audit Events, query filters, retention policy, and the `Store` interface. Execution code depends only on its `Writer` interface. Read-only controllers depend only on `Reader`. PostgreSQL is an adapter in `server/core/runs/postgres`.

Lifecycle observers decorate the existing pull-command and project-command seams. Output persistence decorates the existing project command-output handler and batches terminal lines into moderately sized chunks before calling `AppendOutput`. This keeps persistence logic out of controllers, Terraform step runners, and VCS adapters.

The drift package keeps its existing `Storage` and `RemediationService` interfaces. A PostgreSQL drift adapter reuses the same database pool and migrations but does not route drift behavior through the generic RunStore. Drift detection and remediation also create Runs so the global timeline can link to their authoritative drift records.

## Lifecycle rules

- A Run ID is generated before an accepted operation starts, using UUIDv7.
- One Run covers one logical plan, apply, import, state removal, unlock, drift detection, or remediation request.
- An autoplan is distinguished from an explicit plan by its trigger.
- A Project Run covers one project within the Run. Policy checks generated by a plan update the same Project Run rather than creating an unrelated Run.
- Runs and Project Runs are append-and-complete records. Completed history is not deleted when a pull request closes or is unlocked.
- Duplicate accepted webhook deliveries receive distinct Run IDs. Store uniqueness constraints prevent either delivery from overwriting the other; delivery identifiers are retained in metadata when the VCS supplies them.
- Plan statistics retain add, change, destroy, import, and forget counts.
- Audit Events are a secondary timeline, not an event-sourced write model.

## Failure behavior

When PostgreSQL history is configured, Atlantis validates connectivity and applies migrations before serving requests. Startup fails if that cannot be completed safely.

After startup, RunStore write failures are reported through logs and metrics but do not change Terraform command semantics. The history module is observational in Phase 1 and must not become a hidden execution lock or queue. Failed completion writes leave an obviously incomplete running record that operators can detect rather than falsely claiming success.

When history is not configured, a no-op Store preserves existing Atlantis behavior and no history routes are registered.

## Output and authorization

Raw Terraform output can contain secrets. All history and audit routes require Atlantis web Basic Auth; when `--web-basic-auth` is disabled the routes return not found. The controller verifies credentials in addition to the existing global middleware. The initial implementation does not add apply or remediation controls to the UI.

Output writers preserve order per Project Run, distinguish stdout, stderr, and system output where the existing execution path supplies that information, and flush by size or operation completion. They do not insert one database row per terminal line.

The read-only, server-rendered history surface follows existing Atlantis UI conventions:

- `/runs` provides global repository, pull request, commit, actor, command, and status filters.
- `/repos/{repository}` provides repository-scoped run history, including nested group paths, and `/repos/{repository}?pull={number}` adds the pull-request filter.
- `/runs/{run-id}` provides aggregate status counts, project filters, pagination, and related pull-request runs.
- `/runs/{run-id}/projects/{project-id}` provides summary counts, artifact metadata, and paginated typed output.
- `/audit` provides repository, pull request, actor, event, and date-range filters.

## Initial relational model

The first migration creates `runs`, `project_runs`, `run_output_chunks`, and `audit_events`. UUIDv7 values are generated by Atlantis rather than PostgreSQL. JSON metadata is optional and is not used for fields needed by primary UI filters.

Important constraints include:

- primary keys on every record ID;
- a foreign key from Project Runs to Runs;
- a unique `(project_run_id, sequence)` output ordering key;
- non-negative plan summary counts;
- completed timestamps required for terminal states;
- indexes supporting repository, pull request, commit, command, status, actor, and time filters.

## Retention

Retention is independently configurable and defaults to:

- Run and Project Run metadata: indefinite;
- Audit Events: indefinite;
- raw command output: 90 days;
- S3-compatible plan artifacts: managed independently through object-store lifecycle policy;
- drift history: at least 12 months.

Deleting output or an expired plan artifact must not delete its Run or Project Run. Partitioning is deferred until measured volume justifies it.

## Pull-request stack

The implementation is kept within seven new open pull requests so the existing fork pull request plus this stack stays within Atlantis's eight-PR contributor limit:

1. Run domain, Store interfaces, architecture, and no-op adapter.
2. PostgreSQL RunStore, migrations, configuration, and retention.
3. Plan/apply/import/unlock lifecycle and chunked-output observers.
4. Read-only history and audit UI using existing server-rendered conventions.
5. Compact large-run VCS summaries linked to the durable UI.
6. PostgreSQL latest-state drift storage using the existing drift interface.
7. Durable remediation and append-only drift history plus stale-check UI.

Each layer carries its own tests and operator documentation and may contain multiple cohesive commits. Upstream-derived and fork-specific work is tracked separately so a future upstream merge can remove local patches cleanly.
